# Brightloop Subscriptions

A subscription management and recurring billing system for Brightloop Software. It covers products and plans, quotations, subscriptions, automatic invoicing, discounts, taxes, payments, revenue reporting and a self-service customer portal.

**Live:** https://subscription-plan-rho.vercel.app

## Features

**For admins and staff**

- **Catalogue:** products with sales and cost prices, taxes, and variants that add an extra price (for example, Brand: Odoo +560).
- **Plans:** price, billing period (daily, weekly, monthly or yearly), minimum quantity, availability dates, and rules for whether a customer can pause, renew, close early or auto-close.
- **Quotation templates:** reusable plans, product lines, payment terms and validity periods. A new subscription can be created from a template in one step.
- **Subscriptions:** numbered `SUB-00001` and onwards. Each one moves through **Draft → Quotation → Confirmed → Active → Closed**. Lines stay editable until confirmation and are locked after that. Quotations can be printed and expire after their validity period.
- **Billing:** a daily scheduled run invoices every subscription that is due and catches up any missed periods. Staff can also run billing by hand or bill a single subscription immediately. A period can never be billed twice.
- **Discounts:** fixed or percentage, with an optional minimum purchase or quantity, date range and usage limit. A discount can apply to specific products or to a whole subscription.
- **Invoices and payments:** taxes and discounts are calculated automatically. Invoices can be confirmed, sent by email, cancelled or printed. Partial payments are allowed and overpayment is rejected.
- **Dashboard:** active subscriptions, MRR, revenue collected, amount invoiced, outstanding and overdue amounts, a 12-month revenue chart, and the status of the billing schedule.
- **People:** customer records with balances and history. Admins can invite staff by email and change user roles.
- **Overdue reminders:** optional daily emails for overdue invoices, sent at most once a week and three times per invoice.

**For customers (`/portal`)**

- View their own subscriptions, invoices, quotations and the history of each subscription.
- Pause, resume, renew or cancel a subscription when its plan allows it.
- Pay invoices, print them, and update their own profile.

## Tech stack

- **Next.js 15** (App Router, Server Components, Server Actions), React 19, TypeScript
- **Supabase:** Postgres, Auth, row-level security, `pg_cron`
- **Tailwind CSS 4**
- **Resend** for email (optional)
- **Vercel** for hosting and the reminder cron job
- **Playwright**, Node's built-in test runner, and GitHub Actions for testing and CI

## How it works

Most business rules live in the database, so the same checks apply whether a change comes from the app, the API or SQL.

- **Roles:** `admin`, `staff` and `customer`, enforced with Postgres row-level security. Customers can only read and change their own data. New sign-ups are customers. Only admins can invite staff or change roles.
- **Lifecycle rules:** database triggers enforce subscription and invoice status transitions, plan minimum quantities and availability dates, quotation expiry, and the lock on lines after confirmation.
- **Billing engine:** `_run_billing()` issues invoices for every due period in one transaction. A unique index on (subscription, period) prevents double billing. `pg_cron` runs it daily at 00:30 UTC.
- **Integrity:** invoices can only be created by billing, and their amounts cannot be edited afterwards. Payments keep each invoice's paid amount in sync and mark it Paid when it is settled. Cancelling an invoice gives back the discount uses it consumed.
- **Reporting:** dashboard totals come from SQL aggregates (`dashboard_summary`). List pages are paginated and indexed, and they stay under 2 seconds with thousands of rows.

## Getting started

### Prerequisites

- Node.js 20 or later (CI uses Node 24)
- A Supabase project

### 1. Install

```bash
git clone https://github.com/abhishiv17/Subscription-Plan.git
cd Subscription-Plan
npm install
cp .env.example .env.local
```

Fill in `.env.local` (see [Environment variables](#environment-variables)).

### 2. Set up the database

Apply the migrations in `supabase/migrations/` in order (`0001` to `0010`). Either run `supabase db push` against your linked project, or paste each file into the Supabase SQL editor. Migration `0008` needs the `pg_cron` extension, which you can enable under Database → Extensions.

Optionally, load the demo data in `supabase/seed.sql`: a sample catalogue and plans, 2,000 customers, 3,000 subscriptions and about 7,000 invoices generated by the real billing engine. The seeded customers have placeholder email addresses, so keep overdue reminders turned off while that data is present.

### 3. Configure Supabase Auth

In Authentication → URL Configuration:

- Set **Site URL** to your app's address (for local development, `http://localhost:3000`).
- Add these redirect URLs: `/auth/callback`, `/reset-password` and `/accept-invite` on that address. For local development, `http://localhost:3000/**` covers all of them.
- Set up custom SMTP if you need reliable invitation and password-reset emails. Supabase's default sender only delivers to members of your project team.

### 4. Create the first admin

Sign up at `/signup`, then promote that account in the SQL editor:

```sql
update public.profiles set role = 'admin' where email = 'you@example.com';
update auth.users
  set raw_app_meta_data = raw_app_meta_data || '{"role": "admin"}'
  where email = 'you@example.com';
```

From then on, invite staff and manage roles from `/users`.

### 5. Run

```bash
npm run dev        # http://localhost:3000
```

## Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Yes | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Yes | Supabase anon (publishable) key |
| `SUPABASE_SERVICE_ROLE_KEY` | Yes | Server-only key used for invitations and admin actions. Never expose or commit it. |
| `NEXT_PUBLIC_SITE_URL` | Yes | The app's public address, used in auth redirects and email links |
| `RESEND_API_KEY` | No | Turns on invoice and reminder emails. Without it, "Mark sent" only records the date. |
| `INVOICE_FROM_EMAIL` | No | Sender address for invoice emails |
| `CRON_SECRET` | For reminders | Bearer token that Vercel Cron sends to `/api/cron/overdue-reminders` |
| `REMINDERS_ENABLED` | No | Set to `true` to actually send reminders. Otherwise each run is a dry run. |
| `REMINDER_BATCH` | No | Maximum number of reminders per run (default 50) |
| `DEMO_TEST_PASSWORD` | Tests only | Password of the test admin used by the live test suites |
| `SUPABASE_DB_URL` | Tests only | Postgres connection string for `npm run test:db` |

## Scheduled jobs

| Job | Schedule | Where |
|---|---|---|
| Daily billing | 00:30 UTC (06:00 IST) | `pg_cron` job `daily-billing` (migration `0008`) |
| Overdue reminders | 03:30 UTC (09:00 IST) | Vercel Cron → `GET /api/cron/overdue-reminders` (`vercel.json`) |

To preview the reminders without sending any, call the route with `?dryRun=1` and the `Authorization: Bearer $CRON_SECRET` header. To check recent billing runs, run this SQL:

```sql
select * from cron.job_run_details order by start_time desc limit 5;
```

## Testing

| Command | What it does |
|---|---|
| `npm run lint` / `npm run typecheck` / `npm run build` | Static checks |
| `npm test` | Unit tests. No network access needed. |
| `npm run test:db` | Runs `supabase/tests/database_test.sql`, which covers status transitions, billing maths, discounts, double billing, payments and RLS isolation. Needs `SUPABASE_DB_URL`. All changes are rolled back. |
| `npm run test:live` | End-to-end suites against a running app on port 3001. Needs `DEMO_TEST_PASSWORD`. |
| `npm run test:e2e` | Playwright smoke test: sign up → bill → pay. Run `npx playwright install chromium` first. |
| `npm run perf` | Times the list pages. The median must stay under 2 seconds. |

The live suites create their own test records and temporary accounts, briefly give one of those accounts staff access, and delete everything afterwards. Run them only against a project you are allowed to test on. `supabase/tests/perf_check.sql` times the list queries at 5,000 subscriptions and 20,000 invoices inside a rolled-back transaction.

**CI** (`.github/workflows/ci.yml`) runs lint, type checks, the build and the unit tests on every push and pull request. It also runs the database tests when the `SUPABASE_DB_URL` secret is set. The live suites, Playwright and the performance check run when the workflow is started by hand with **live** selected.

## Deployment

The app is deployed on Vercel. Every push to `main` triggers a new deployment.

1. Import the repository into Vercel.
2. Add the environment variables listed above to the Vercel project.
3. Add the production address to the Supabase Auth URL settings (see step 3 of Getting started).
4. To turn on overdue reminders, set `CRON_SECRET`, `RESEND_API_KEY` and `REMINDERS_ENABLED=true`.
